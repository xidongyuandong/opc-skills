# 构建、登记与验收

## 预检与边界

从当前 skill 位置定位相邻核心目录，不使用作者机器路径。检查 Ruby 可运行；Node.js 用于离线执行脚本和回归。GUI 用现场可用的控制工具；没有 GUI 工具时把明确的人工操作交给用户，完成前保持“待 GUI 登记”。

读取源配置的结构和原卡片类型、显示名称、专属增强绑定；只输出计数、键名和必要显示名称。记录原文件哈希、current、系统代理和 TUN 状态。源文件与合成配置不同：现有 Merge/Script 可能承载必要规则，必须识别后在候选中保留；不能盲目拷贝并共享可写 sidecar。

核心生成器前提是 `proxies` 内有具体可用节点、已有可选择的入口组。仅 `proxy-providers/use` 的配置、纯 direct 配置、入口组为 url-test/fallback、同名代理/组、已有未知 dialer 链时，先给出缺口并选择明确的适配方案；不要直接喂入核心生成器。尤其不要把既有静态代理再次选为自己的上游。

核心模板会从具体代理中选 Auto-Best 成员，且会替换指定同名自定义对象。为新构建选择不与原对象冲突的名字；新静态代理名称只来自私有参考 YAML。已存在静态链时不要自行“再套一层”：请用户明确新增地区、替换出口还是仅登记现有配置。

## 候选生成：Local 与 Remote 共用同一 sidecar 算法

在私有工作目录用 YAML 序列化库生成 provider/reference YAML，只有所需静态节点；参数至少包含 name/type/server/port 与供应商明确的认证、TLS/UDP 设置。不要拼接 YAML 文本处理含冒号、引号或换行的密码，不将真实值放进命令参数。核心支持协议字段透传，但是否有效由 Mihomo 验证；HTTP/SOCKS5 以外的资料先核验协议，不冒充兼容。

以下是变量化命令示意；由执行 agent 从现场解析绝对路径和名称后填入变量。`core_dir` 是相邻核心目录，`reference_file` 是私有参考文件，`candidate_script` 必须是新的私有输出，名称不允许覆盖源对象。

```bash
umask 077
ruby "$core_dir/scripts/build_static_ip_sidecar.rb" \
  --reference "$reference_file" --proxy-name "$static_proxy_name" \
  --entry-group-name "$entry_group_name" --auto-group-name "$auto_group_name" \
  --static-group-name "$static_group_name" --output "$candidate_script"
```

仅在用户要求时增加 `--exclude-regex`，Ruby 和 JavaScript 正则语义需实际执行核验，不能仅依赖 Ruby 编译成功。不要使用 `--force` 覆盖未审阅文件。

用 Node.js 将脚本加载到独立上下文，调用 `main(config, profileName)`；输入是安全解析后转 JSON 的源配置。JSON 读取和 YAML 写出用结构化库，输出权限 600。不要从 stdout 打印整个结果；直接存储候选。原 sidecar 若已有必要转换，按当前应用真实执行顺序保留并组合，在隔离环境验证后再登记。不能把原脚本悄悄丢弃。

验证两次调用结果一致，再模拟上游增加/删除节点，证明 Auto-Best 引用重建；零候选必须失败。核对无循环、唯一名称、所有引用存在、静态组仅含静态代理。核心 verifier 只覆盖部分结构，不替代这些额外检查。

```bash
ruby "$core_dir/scripts/verify_sidecar_profile.rb" \
  --profile "$candidate_yaml" --static-proxy-name "$static_proxy_name" \
  --entry-group-name "$entry_group_name" --auto-group-name "$auto_group_name" \
  --static-group-name "$static_group_name"
```

若已发现 Mihomo，使用其 `-t -f` 检查最终合成。注意该检查可能下载 provider 数据或写缓存，应使用隔离目录并说明网络需求；无内核时记录“仅结构验证”。

这里统一复用 sidecar 算法，不调用会重写 MATCH 的 legacy direct-YAML builder；不自动改规则覆盖范围。生成器会将静态组置于入口可选项首位，但应用可能恢复历史选择，必须检查实际运行态，不能凭首位推断生效。

## Remote：更新不覆盖静态链

1. 从原 Remote 元数据安全取得 URL；不在输出回显。无法取得时提示用户在原卡片编辑界面提供可用订阅或私有 URL 文件。
2. GUI【订阅】→ 新建 Remote，使用同一基础订阅链接，名称为“原显示名称-地区”。用户提供资料已授权本地新增时连续完成保存。
3. 对新卡片右键 →【编辑扩展脚本】（按版本可能称 Script/配置增强），保存候选脚本或已验证的合并脚本。必须是订阅专属脚本，不修改全局脚本，不复用原卡片的可写脚本 UID。
4. 只读核验新条目的 UID、类型、名称和独立绑定，核验所绑定文件确实有可执行静态链重建逻辑。仅 script UID 存在不能证明增强成功。
5. GUI 可见是独立验收门槛。每次更新先对比最新原始下载配置与本次保留名称（静态代理、Auto-Best、静态出口组），三者均不能与供应商节点或组碰撞；初次无碰撞不代表以后无碰撞。核心模板会替换同名对象而不报错，出现碰撞时更新保护验收必须失败，停止候选启用，重新选择唯一名称并重建后才继续；若已经启用则按已授权的回滚流程恢复原选择。不得仅凭最终链完整或脚本哈希判定更新成功，也不承诺无人值守永久更新安全。普通更新及“更新（代理）”成功后检查最终合成和脚本哈希；前者失败排查 URL/授权，后者额外排查当前代理/DNS。不能通过覆写整个 profiles.yaml 修复。
6. 若用户已经授权启用，切换并完成下节出口验证；否则保持 current，说明生效层尚待切换。

## Local：独立 YAML 导入

1. 将上述合成候选作为独立配置，确认来源的业务规则与增强已经纳入且当前文件未修改。
2. 保持应用运行，GUI【订阅】→ 新建 → Local/本地配置 → 选择候选文件 → 填“原显示名称-地区”→ 保存；支持拖入 YAML 的版本也可导入后修改新卡片名称。
3. 通过 GUI 确认卡片可见；只读核验登记 UID 恰好一次、type=local、正式 YAML 存在且结构等同候选；原卡片和 current 保持约定。
4. Local 是独立快照，更新上游需重新构建；不能承诺订阅更新按钮会维护上游。需要自动更新时使用 Remote 分支并取得有效 URL。

禁止应用运行时直接改 `profiles.yaml` 再退出保存。不要删除未核实引用的临时文件；候选存在不等于注册成功。已有核心旧参考中机器专属同步器、历史地点、宽泛重启建议不适用于此通用入口，不调用作者机器脚本。

## 运行态与失败反馈

授权启用后记录原 current 和组选择；Rule 模式检查规则实际引用入口组，Global 模式检查 GLOBAL，均选择静态出口组而非 auto-best。直连规则保持直连。Auto-Best 只是连接静态服务的上游，选中它作为最终出口会绕过静态 IP。

通过当前 Mihomo 的实际代理端口或同等受控通路查询两个独立 IP 来源，结合供应商的预期出口、国家/城市/ISP 核验。不要硬编码端口。IPPure 页面可作为辅助，但 HTTP 200 不代表它成功检测 IP。静态服务地址可能不等于出口 NAT 地址；没有供应商出口信息时，只报告测得 IP/地区，不能声称精确匹配。

|阻塞|反馈与下一步|
|---|---|
|缺协议/端口/认证/地区|列出缺项与输入提示，保留原配置，不购买、不猜测|
|源 YAML 解析失败|仅报告文件与行号，不显示周围敏感原文；请提供可解析副本|
|没有合格上游或循环|明确阻断，调整用户认可的排除规则或提供普通订阅节点；不回退 DIRECT|
|GUI 操作不可用|交付候选与准确人工导入步骤，登记仍未完成；不能凭索引猜测卡片可见|
|新增卡片重名|只复用可证明属于本次的条目，否则暂停该写入并询问|
|订阅 403/代理更新失败|保留原卡片，分别记录两种更新结果；不宣称 Remote 更新保护验收完成|
|结构成功而公网不符|先核验实际选项及 dialer 方向，再查认证、供应商出口与检测链路|

## 撤销本次新增

未启用时，用户确认移除后通过 GUI 仅删除本次新卡片；删除其专属脚本前确认没有其他引用。已启用时先按授权恢复原 current/组选择并核对联网，再撤销新卡片。只清理本次无引用产物，不替换整个索引、全局 DNS、系统代理或原订阅。使用已有备份恢复本次受控文件时，检查期间用户是否另有改动，不能覆盖新改动。
